# Display Link Notes (Single-Cable Dual Monitor · DP 1.4 MST)

[简体中文](display-link-notes.md) · **English**

> Entry point: [`../README.en.md`](../README.en.md).

> **Scope**: the display link of the single-cable dual-monitor setup — one DP cable carrying two monitors over
> MST (`card1-DP-4` top / `card1-DP-6` bottom). The "legacy file" referenced below is
> [`legacy-fix-boot-black-screen.sh`](legacy-fix-boot-black-screen.sh) in this directory (verbatim archive,
> **archive only, do not run it**: its root-cause verdict and its `DP-5`/`DP-11` connector names are obsolete,
> see §0).

## 0. First, the legacy file's verdict on the black screen has been superseded

The legacy file attributed the black screen to two things: (1) the system being switched to
`system-update.target` (offline-update mode, which by design does not start a desktop), with `rhgb quiet` +
plymouth failing to render on this MST link → total blackout; (2) KDE Discover's `UseOfflineUpdates=true`
staging updates to run on the next boot.

**Neither is the primary cause on this machine.** The primary cause is unstable DP link training: every boot
reports `LTTPR count is nonzero but invalid lane count` + `lttpr_caps phy_repeater_cnt is 0x0, forcing it to
0x80`, and at the first real modeset amdgpu hits an MST payload allocation race →
`Atomic modeset commit failed! Invalid argument` (EINVAL). See the background section of
[`../README.en.md`](../README.en.md).

The **link-side** content of the legacy file is still valid — notably it explains why the core patch
"greeter pinned at 120Hz" must exist, so the sections below are kept by topic.

## 1. Bandwidth budget: why 120Hz is mandatory

| Item | Value |
| --- | --- |
| One monitor 2560x1440@180Hz | ≈ 16.4 Gbps |
| Both monitors @180Hz | ≈ **32.8 Gbps** |
| DP1.4 (HBR3, 4 lanes) effective payload | ≈ **25.9 Gbps** |
| Both @144Hz | ≈ 26.7 Gbps — **still above the DP1.4 limit**, needs DSC, little point |
| Both @120Hz | ≈ **21.9 Gbps** — back inside DP1.4, likely without DSC at all |

Over the limit you must lean on DSC, and once DSC is in play MST slot payload allocation fails more easily
(observed in logs: `MST_DSC` + `allocate_mst_payload` WARNING + the `DM_MST` topology manager restarting
repeatedly) → black screen. **That is why the greeter is pinned at 120Hz — not for power.**

Runtime refresh-rate change (take the connector names from the current boot via
`ls /sys/class/drm/card1-DP-*`; this machine currently has `card1-DP-4`/`card1-DP-6` — the `DP-5`/`DP-11`
names in the legacy file come from an earlier boot and are dead):

```bash
kscreen-doctor output.DP-4.mode.2560x1440@120 output.DP-6.mode.2560x1440@120
# observe for a day or two; if still black, drop one more notch:
kscreen-doctor output.DP-4.mode.2560x1440@100 output.DP-6.mode.2560x1440@100
```

(System Settings → Display and Monitor works equally well.)

## 2. Monitor OSD side (no cable swap, no rewiring)

- DP version: "Auto" → fix at **1.4**
- DSC: **try one round on, one round off** (some machines are more stable with DSC on, others the opposite)
- Turn off **FreeSync / Adaptive-Sync**, turn off **HDR**, fix colour depth at **8 bit**
- Confirm you are on **MST**, not the monitor's internal **PBP** mode

## 3. Firmware side

Flash the **motherboard BIOS (AGESA)** and the **monitor firmware** — most MST / LTTPR fixes land there.
(Consistent with the current investigation: this machine reports an LTTPR misread on every boot, which is why
"try a different DP cable" is listed as a candidate measure.)

## 5. Verification (run after a reboot; counters should drop to ~0)

```bash
journalctl -b -1 -k | grep -cE 'allocate_mst_payload|Unsupported screen format|LTTPR'
journalctl -b -1 | grep -c 'Atomic modeset commit failed'
journalctl -b -1 | grep -oE 'default target [a-z.-]+' | sort -u   # should be back to graphical.target
```

## 6. Self-rescue when the screen goes black again

- Don't rush to reboot (a reboot interrupts an offline update that may be running)
- Press `Esc` to see the boot log; press `Ctrl+Alt+F3` to switch to a TTY
- If you can reach a TTY the system is alive — most likely it is installing updates, or the display
  configuration did not apply
- Check: `ls -l /system-update`
